# AI News Fetcher

## Overview

最新のLLM／生成AIニュースを調査し、tarikicode-svelteのブログ形式で日本語記事を作成するためのスキル。調査 → 一次ソース照合 → 構成 → 執筆 → セルフチェックの順に進める。

このスキルは、過去の記事へのファクトチェック指摘から得たルールを含む。各ルールの「なぜ」は末尾の「ルールの由来」を参照。`references/blog_template.md` の例文と食い違う場合は、このファイルを優先する（特に太字の量）。

## When to Use This Skill

- AIニュース記事（日本語）の作成を依頼されたとき（`/ai-news` コマンド経由を含む）
- ChatGPT、Claude、Gemini、DeepSeek等の最新動向をブログ記事にするとき

## Workflow

### Step 0: 事前確認

1. `date +%Y-%m-%d` で今日の日付を確認し、対象期間（通常は過去7日間）をユーザーに明示する
2. `src/posts/` の直近2週間程度の記事タイトルを確認し、同じモデル名・同じ企業の同じニュース・同じ技術が主題の記事を避ける

### Step 1: Research（情報収集）

#### 候補探し

- WebSearchを最低3回。主要企業（OpenAI、Anthropic、Google、DeepSeek、Meta、Mistral、xAI等）とリリーストラッカーを確認する
- トラッカーやWebSearchのサマリは候補探しにだけ使い、記事の事実には使わない

#### 一次ソースでの照合（必須）

次の項目は、必ず提供元の公式ページで直接確認する。二次ソース（VentureBeat、TechCrunch、9to5Mac等）が複数一致していても代わりにはならない。

| 項目                                                            | 確認先                                            |
| --------------------------------------------------------------- | ------------------------------------------------- |
| 価格・キャッシュ・Batch・長文脈の料金段階                       | 公式pricingページ                                 |
| APIパラメータの列挙（effortの段数・名前・既定値）               | 公式APIドキュメント                               |
| 提供プラン・提供範囲・ロールアウト段階（GA／preview／地域限定） | 公式ブログ・changelog                             |
| API挙動（拒否時の動作、フォールバック等）                       | APIリファレンス（製品ページのマーケ表現ではなく） |
| ベンチマーク数値と測定条件                                      | System Card等のPDF本文                            |

ベンチマークは、公式ページの画像やWebFetchの要約ではなくPDF本文で確認する。WebFetchが画像・サイズ超過で失敗する場合や、要約だけでは不安な場合は次の手順を使う。

```bash
D=<scratchpad>/sc; mkdir -p $D
curl -sL -o $D/card.pdf "<System Card URL>"
pdftotext -layout $D/card.pdf $D/card.txt
grep -n -i -E "<ベンチマーク名>|effort|trials|averaged" $D/card.txt
```

数値ごとに次の4点を確認し、記事に書き分ける。

1. 測定条件：effortレベル（max／既定値など）、思考モード、試行回数、ツールの有無
2. 実行者：自社実行か、第三者（Artificial Analysis、Cognition等）か
3. 競合列の出どころ：発表元が競合の公式資料から引用した値か、公開リーダーボード値か、発表元が自分で走らせた値か
4. 既定設定での値：主要数値が最大設定で測られている場合、既定設定の値が載っていないかを探す

#### 価格比較のルール

- 比較表に並べる価格は、同じAPI種別・同じ課金体系（標準ティア・従量課金など）・同じトークン単位で揃える。揃えられない場合は注記する
- 長文脈の料金段階、期間限定価格、改定予定は注記する
- 「○%安い」は同一条件で確認できたときだけ書く。公式の比較対象（"comparable models" 等）を具体モデル名に置き換えない
- 予算や倍率の比較では基準（当初予算／補正込み、平均／最大など）を明記する

### Step 2: 構成

ニュースの種類に応じて骨組みを選ぶ。

| 種類             | 構成                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------ |
| 新モデル発表     | 導入 → サマリー表 → 基本スペック → 価格 → ベンチマーク（測定条件込み） → 実務上の注意点 → まとめ |
| 機能アップデート | 導入 → 何が変わったか → 技術的な詳細 → 使いどころ → 旧版との比較 → まとめ                        |
| 業界動向         | 動向の概要 → 主要データ → 主要プレイヤーの戦略 → 日本への示唆 → まとめ                           |

導入は身近なたとえや問いから入り、記事の主題（数字の裏にある論点）を早めに示すと読みやすい。

### Step 3: 執筆

#### Frontmatter

```yaml
---
title: '<タイトル>'
date: 'YYYY-MM-DD' # Step 0で確認した今日の日付
category: 'AI'
tags: ['製品名', '企業名', 'トピック'] # 3〜5個
description: '<100〜160文字>'
image: '<公式ページのog:image等>'
featured: false # 主要な新モデル発表など大きなニュースは true
type: 'blog'
---
```

#### タイトル

- 具体的な数値や論点を入れる。区切りのダッシュは `──`（U+2500）を使う
- 長さは原則60字以内（英数字も1字と数える）。`python3 -c "import sys;print(len(sys.argv[1]))" '<タイトル>'` で確認する
- 60字に収めるため、細かい数値（例：既定設定でのスコア）はdescriptionや本文の冒頭に回す
- 本文冒頭のh3見出しもタイトルと同じ文言にそろえる。既存記事にはさかのぼって適用しない

#### 文章の考え方

AIが書いたような文章を避けるコツは、「その人にしか書けない要素」を入れることにある。ニュースの要約で終わらせず、読者がついてこられるように順を追って説明する。

##### 実体験と主観（著者が書く部分）

- 実際に触った結果、うまくいかなかった点、なぜこの記事を書こうと思ったかは、著者にしか書けない。AIが体験や感想を作ってはいけない
- 体験を入れると効果的な箇所には、`<!-- 実体験：〜（例：mediumとmaxを自分のタスクで比べた結果） -->` のようなHTMLコメントを置き、著者があとで補足できるようにする（ページには表示されない）
- 「個人的に注目しているのは〜」「これは正直微妙で〜」のような主観は、著者とすり合わせてから書く。AIが下書きした主観の段落は、完了報告で「要確認」として伝える

##### 比喩と噛み砕き

- 専門用語は初出時にカッコで日本語の補足を添える（例：Function Calling（関数呼び出し）、effort（どれだけ考えるかの設定））
- 厳密な定義は「すごく雑に言うと」で噛み砕く。比喩は身近なものを大胆に使う（例：コンテナを「使い捨ての仮想PC」）
- 抽象 → 具体 → 比喩の3段階で説明すると伝わりやすい

##### 読者に寄り添う

- 「ここだけ押さえればOK」「他はデフォルトのままでよい」のような安心できる一言を入れる
- 読者がハマりそうな点（料金の境界、既定値の違い等）は先回りして説明する
- 前提知識を仮定しすぎない。初めてそのモデルを知る読者がついてこられるかを意識する

##### 情報密度

- 箇条書きは3〜4項目まで。多くなるなら分割するか本文で説明する
- 箇条書きの階層は1段まで（深くても2段）。各項目は1〜2文で、長くなるなら本文に戻す
- 1段落1トピック。詰め込まず、前の段落の理解の上に次を積み上げる

#### 本文

- 見出しは h3（###）→ h4（####）→ h5（#####）の階層で使う。h2は使わない
- 比較は表で示し、具体的な数値・日付を入れる
- 一人称が必要なときは「私」。「筆者」は使わない
- Mermaid図を使う場合は、箱7個程度の大まかな流れにとどめ、表の項目を網羅しない
- 検証の過程（「裏取りできなかったため〜」等）は本文に書かない。結論と読者にとっての実務的な意味だけを書く

#### 太字

- 記事全体で5〜10箇所、1セクション1〜2箇所まで。読者に覚えて帰ってほしい結論にだけ使う
- 表のセル、箇条書きの先頭、名詞句には使わない
- 句読点・鉤括弧は太字の外に出す。marked（12.0.2）は `**…です。**鮮度は` や `**「…」**という` を強調として認識せず、`**` がそのまま表示される
    - ✅ `**…です**。` ／ `「**…**」`
    - ❌ `**…です。**続く文` ／ `**「…」**`

#### 情報ソース

記事末尾に、一次ソースを先、二次ソースを後にして、OGPカード記法で並べる。各行の間には空行を入れる。

```markdown
**情報ソース：**

[[ogp:https://example.com/official-announcement]]

[[ogp:https://example.com/news-article]]
```

### Step 4: 保存

- パス：`src/posts/YYYY-MM-DD-slug.md`（slugは小文字英語をハイフン区切り）
- 保存後に `npx prettier --write <file>` と `npx markdownlint-cli2 <file>` を実行する

### Step 5: セルフチェック

#### 断定・帰属・因果

次の語を含む文を抜き出し、それぞれが一次ソースの明示的な記述に対応するか確認する。

`〜することで` `初` `唯一` `最大` `〜と位置づけた` `解決` `つまり` `と読める` `〜されない`

- 一次ソースで別々に書かれている事実を「〜することで〜を実現」とつなげない
- 「初」「最大」は一次ソースに明記があるときだけ書き、主語（「Anthropicによると」等）を添える
- 公式の並列表現（"resolves or makes progress"）を片方に縮めない。タイトル・description・表・まとめも同じ
- 媒体の論調として書く（「Bloombergは〜と位置づけた」）のは、本文を確認できた場合だけ
- 「〜されない」等の全称否定は、例外事例（緊急提供、特定地域等）を検索してから書く
- 「低い」「高い」は比較対象を明示する
- 公式が明記している事実を「メディアの分析」に弱めない
- モデルの系譜（後継・派生）を推論で書かない

#### 横断確認

同じ事実はタイトル・description・サマリー表・本文・まとめに繰り返し出る。1箇所を直したら `grep -n "<旧表記>" <file>` で全箇所を確認する。

#### チェックリスト

- [ ] Frontmatter完備、日付は今日、descriptionは100〜160文字、タグ3〜5個
- [ ] 価格・列挙・提供範囲・ベンチマークは一次ソースで照合済み
- [ ] ベンチマークに測定条件（effort等）と実行者を添えた
- [ ] 価格表の課金体系が揃っている、または注記がある
- [ ] 太字は5〜10箇所、句読点は太字の外（`grep -n '\*\*' <file>` で確認）
- [ ] タイトルのダッシュは `──`
- [ ] 比較表とまとめセクションがある
- [ ] 専門用語に初出時の補足がある。箇条書きは3〜4項目・1〜2文まで
- [ ] 体験や感想を作っていない。体験を入れる箇所に `<!-- 実体験：〜 -->` を置いた
- [ ] 情報ソースは `[[ogp:URL]]` 形式で一次ソースが先
- [ ] 既存記事と重複していない
- [ ] prettier と markdownlint が通る

## ルールの由来

| ルール                               | 由来となった指摘                                                                                         |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| effortの列挙は公式docsで確認         | 2026-05-31 Opus 4.8記事：二次ソースの「extra」を採用し、正しくは `xhigh` の5段階だった                   |
| 提供範囲は狭すぎ・広すぎの両方に注意 | 同記事：「Copilot全プランで一般提供」と書いたが、実際はPro+／Business／Enterprise限定かつgradual rollout |
| API挙動はAPIリファレンスで確認       | 2026-06-10 Fable 5記事：製品ページの「自動ルーティング」を技術仕様として書いた                           |
| ベンチマークはPDF本文で照合          | 2026-07-04 Sonnet 5記事：複数の二次ソースが一致していたが、ベンチマーク名の取り違えだった                |
| 価格表の課金体系を揃える             | 2026-05-23 Google I/O記事：出典条件の異なる価格を並べて「40%安」と結論づけた                             |
| 因果の合成・断定の禁止               | 2026-07-19 Kimi K3／Inkling記事、2026-08-08 Astra記事                                                    |
| 全称否定は例外を検索                 | 2026-09-27 政府AI予算記事：被災自治体への緊急提供を見落とした                                            |
| 既定設定での値を探す                 | 2026-10-12 Haiku 5.5記事：公表値はmax effort、既定のmediumではGDPval-AAが1620→1277                       |
| 太字は5〜10箇所                      | 2026-05-23 Google I/O記事：48行に太字が散在し、何も目立たなかった                                        |
